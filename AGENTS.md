# AGENTS.md

## What this is

OpenRP is a native desktop roleplay AI engine, built on the [SereChat](https://serechat.com) API. Today it has sign-in, Worlds and Characters pages (index plus a form with name, description and portrait, and Duplicate; a saved world's form lists its stories, which open on click), stories (Play on a world starts a session, which first asks who the user plays and is saved and listed once they Begin; its cast holds copies of library characters, present or absent in the scene, each with a menu to store it in Characters (updating the character it was cast from), edit (name, description, portrait) or delete it, and Add offers From characters, Create character and Generate character (a separate request whose system prompt only lets the model call `create_character`; the result opens for review); the world, player and cast make up the system prompt; deleting a world deletes its stories), no narrator: every reply must call tools (`tool_choice: required`), `speak`: everything characters say and do in a reply as `messages` (character, action, text), one per character (duplicates merge into one bubble and the model is told), shown as they stream as bubbles with the character's portrait; text outside tool calls is dropped (no narration); `speak` takes a required `scene` (the place and ambiance when they change, else empty; kept on the session, sent in the prompt, shown above the cast and editable there by clicking it), an optional `leave` list (members who move out of the scene) and a required `introduce` list (newcomers with descriptions, cast before their lines; the prompt allows newcomers only when the user refers to someone not cast yet or no one is in the scene); no one is cast without a description: someone who acts uninvited is reported and the next request forces `create_character` (a repair round); `create_character` adds someone not acting yet or describes an undescribed member (calls in a reply run creations first); a reply that only called tools continues on its own, at most 3 times), memories (`remember` tool appends facts to the session's `memories`, sent in the prompt, undone with their reply, edited by hand via the Memory button; every 8 prompts, or on `/memorize`, a separate request with `remember` forced reads the turns since the last review and adds more, `stream.rs`), an author's note (session `note`, last in the prompt) and `/ooc` instructions (a line starting `/ooc` in a user message; `stream.rs` marks it for the model, shown muted), duplicating sessions (exact copy with costs zeroed, or a frame: world, player, cast and note only; unloaded sessions are read first), streaming Markdown replies with model and reasoning pickers, retries and context compaction, Spotlight search (Ctrl/Cmd+K; commands, stories also by their world, worlds, characters, models, messages), and a settings page. Tool calls and results are saved on each reply and sent back with the next request (function_call + function_call_output), with a `change` record (cast members before/after, scene before/after) so a turn (a prompt and its replies; `chat/turns.rs`) can be edited (a field per character bubble; saving rewrites the speech in the reply's `speak` call via `tools::respeak`; replies edited into plain text by earlier versions are read back into bubbles by `tools::parse`), regenerated (last turn) or deleted; regenerating or deleting the last turn undoes its changes unless they were changed again since. Characters are a local library to reuse across stories; nothing is uploaded (SereChat stores no characters).

- API: [Responses API](https://serechat.com/docs/responses) (`POST /v1/responses`, SSE streaming); the server's source is in `../serechat` (`app/inference/api/llms/`). tool calls arrive as `function_call` items; results go back as `function_call_output` items (consecutive calls merge into one assistant turn server-side). A stream ends with `response.completed`, `response.incomplete` (`incomplete_details.reason`, e.g. `max_output_tokens`) or `response.failed` (`error.code`: retry `server_error` and `rate_limit_exceeded`, compact on `context_length_exceeded`). `: ping` comments arrive every 15 s. Usage includes `input_tokens_details.cached_tokens` / `cache_write_tokens`; `/v1/models` reports `context_window` and cache prices; `max_output_tokens` defaults to the model's maximum. Reasoning input items are ignored, and there is no server-side conversation state.
- Auth: [device-code flow](https://serechat.com/docs/authentication). On first run the app opens the browser, the user approves, then types the 6-digit code into the app.
- Local data: everything lives in `~/.openrp/`: `config.toml`, `sessions/<id>.json` + `sessions/.index.json`, `worlds/<id>.json`, `characters/<id>.json`, `portraits/`. A session stores its `world` id, `player`, `scene`, `memories`, `note` and `cast` (copies: id, name, description, portrait, present); the prompt reads the world from the library at send time. Another app also uses `~/.openrp/`; keep file names distinct from its. See `README.md`.

See `README.md` for features, the crate layout and the architecture.

## Hard requirements from the owner

- **Fully Rust-native, custom UI.** Use `winit` + `wgpu` and draw every pixel ourselves. No Tauri, no web views, and no UI frameworks (egui, iced, etc.).
- **Stunning, yet extremely fast.** Performance comes first. Redraw only when something changes, do minimal work per frame, and keep the single-pipeline, single-draw-call renderer.
- **Cross-platform:** it must work on Windows, macOS and Linux.
- **Dependencies are costly.** Add one only if it is truly required and can't reasonably be written by hand. No `thiserror`: write custom error types by hand (`Display` + `std::error::Error`). No `anyhow`, no async runtimes (`tokio`), no convenience crates. Disable default features where possible. OS features go through the tools the platform ships with (see `platform.rs`) rather than new crates.
- **Always use the latest versions** of the dependencies we do use.
- **Cargo workspace:** `crates/serechat` is the API client with no GUI deps; `crates/desktop` is the app (package and binary `openrp`).
- **Military-grade code quality, properly documented.** Every public item has doc comments, `clippy::pedantic` stays clean (`cargo clippy --workspace --all-targets`), and there are no `unwrap`s on fallible runtime paths. Non-trivial logic gets a small unit test. Parsers must survive hostile input (bounded recursion, no slicing off char boundaries).
- **Secrets:** never log the token. Write config files atomically, with `0600` permissions on Unix.
- **Safety:** links from replies only open `http(s)`/`mailto`.
- **Testing:** the owner tests the GUI themselves. Don't drive the app with computer use; `cargo build`, `clippy` and `test` are enough. CI (`.github/workflows/ci.yml`) runs clippy with `-D warnings` and the tests on Windows, macOS and Linux; a `v*` tag publishes release binaries.

## Conventions

- Deliberate shortcuts are marked `ponytail:` with their limit and upgrade path. Current ones: fallback fonts are read fully into memory; no complex-script shaping (Arabic, Indic) or bidi; grapheme clusters follow a practical subset of UAX #29; the world and character forms show no input-method preedit; the portrait picker runs a helper process; the config file uses a flat, string-only TOML subset; the exe icon (`build.rs`, from `assets/icon/`) is embedded for MSVC only; macOS gets its icon from the `.app` and Linux from `openrp.desktop`, both made by the release job from `packaging/`.
- Every file the app writes (sessions, worlds, characters, config) goes through the `Writer` thread in `app.rs`, in order; reads run on workers. Two exceptions, both portraits: a picked portrait is copied in on the picker's worker under a fresh name nothing else writes, and the startup sweep deletes unreferenced portraits older than a day (nothing else ever deletes one, since stories share them). Never write files from the UI thread.
- Glyphs and image thumbnails live in two 2048² atlases packed by `atlas.rs`, which evicts the least recently drawn shelf when full. Portraits are drawn with `library::portrait` (over `Painter::image`, which decodes on a worker on first use).
- Screens never touch disk or network: they push `Action`s; the app runs them (on worker threads when slow) and reports back via `WorkerEvent`. Never block the UI thread.
- Colours and sizes live in `crates/desktop/src/theme.rs`. Colours come from the active `Palette` (`p.theme`), never hard-coded, so all three schemes (Dark default, One Dark, Light) keep working. The look is Zed-inspired: flat surfaces, hairline borders, 4–6px radii, one accent, no gradients or glows.
- Text never assumes a font covers it: layouts go through `Fonts::resolve`, which falls back to Twemoji and the system's CJK fonts.
